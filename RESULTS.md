# Results

## Phase 1: Docker Warm-Up

> [!NOTE]
> **Evidence sets:** The top-level files in `evidence/phase1-real-*.txt` record the initial manual interactive `psql` runs. The files in `evidence/phase1/` record the full automated matrix runs generated by `scripts/test-matrix.sh`.

### 1. Target Server Configurations

| Target | Signed by | Names in cert | Description |
|---|---|---|---|
| `real` | CA-A (trusted) | `postgres-real`, `localhost`, `127.0.0.1` | Legitimate server |
| `impostor-wrong` | CA-B (untrusted) | `postgres-wrong` | Untrusted CA and wrong hostname |
| `impostor-correct` | CA-B (untrusted) | `postgres-real`, `localhost`, `127.0.0.1` | Untrusted CA, but with the **correct hostname** ("right name from the wrong CA") |
| `impostor-sameca` | CA-A (trusted) | `postgres-wrong` | **Same cluster CA**, but wrong hostname |

### 2. Connection Matrix

#### Headline: `require` without a CA file
Without a CA certificate provided, `sslmode=require` connected to **every single impostor**:
- `real`: **CONNECTED**
- `impostor-wrong`: **CONNECTED (FOOLED)**
- `impostor-correct`: **CONNECTED (FOOLED)**
- `impostor-sameca`: **CONNECTED (FOOLED)**

#### Results Grid (Client provided with trusted CA-A `root.crt`):

| Target | `require` | `verify-ca` | `verify-full` |
|---|---|---|---|
| `real` | CONNECTED | CONNECTED | CONNECTED |
| `impostor-wrong` | REFUSED* | REFUSED | REFUSED |
| `impostor-correct` | REFUSED* | REFUSED | REFUSED |
| `impostor-sameca` | CONNECTED | **CONNECTED (FOOLED)** | **REFUSED** |

*\* Refused only because `sslrootcert` was provided to libpq. When omitted, `require` accepted every impostor.*

---

### 3. Key Findings

1. **`ssl=on` allows TLS but does not force it:**
   Enabling SSL on the database server does not prevent clients from sending plaintext. With standard access rules, `sslmode=disable` established a session in unencrypted plaintext (`pg_stat_ssl.ssl = f`).
   *Evidence:* [real-disable-without-root.txt](evidence/phase1/real-disable-without-root.txt)

2. **`require` encrypts but trusts anyone:**
   In its standard configuration (no CA certificate mounted), `sslmode=require` encrypts the connection but blindly accepts any certificate presented by the server. It connected to all three impostor servers without warning.
   *Evidence:* [impostor-wrong-require-without-root.txt](evidence/phase1/impostor-wrong-require-without-root.txt), [impostor-correct-require-without-root.txt](evidence/phase1/impostor-correct-require-without-root.txt), [impostor-sameca-require-without-root.txt](evidence/phase1/impostor-sameca-require-without-root.txt)

3. **Providing a CA file quietly upgrades `require`:**
   When an application specifies `sslrootcert`, libpq silently validates the CA signature even if the mode is only `sslmode=require`. Consequently, `require` refused both CA-B impostors when the CA file was present (`SSL error: certificate verify failed`).
   *Evidence:* [impostor-wrong-require-with-root.txt](evidence/phase1/impostor-wrong-require-with-root.txt), [impostor-correct-require-with-root.txt](evidence/phase1/impostor-correct-require-with-root.txt)

4. **`verify-ca` blocks untrusted CAs, but NOT same-CA impostors:**
   `verify-ca` successfully rejected certificates from CA-B, but it completely failed to detect `impostor-sameca`. Because the certificate was stamped by the trusted CA-A, `verify-ca` established a connection despite the wrong hostname.
   *Evidence:* [impostor-sameca-verify-ca-with-root.txt](evidence/phase1/impostor-sameca-verify-ca-with-root.txt)

5. **Only `verify-full` stopped every impostor:**
   `verify-full` was the only mode that prevented connection to `impostor-sameca`. In addition to verifying the CA chain, it strictly enforced hostname matching, catching the spoofed endpoint with:
   `psql: error: server certificate for "postgres-wrong" does not match host name "localhost"`
   *Evidence:* [impostor-sameca-verify-full-with-root.txt](evidence/phase1/impostor-sameca-verify-full-with-root.txt)

6. **Verification modes fail safe when no CA file is found:**
   Both `verify-ca` and `verify-full` refused to connect when no CA certificate was configured, failing closed with `root certificate file ... does not exist` rather than falling back to unverified encryption.
   *Evidence:* [real-verify-ca-without-root.txt](evidence/phase1/real-verify-ca-without-root.txt), [real-verify-full-without-root.txt](evidence/phase1/real-verify-full-without-root.txt)

---

### 4. Limits of Phase 1

This phase tested impostors with untrusted CAs or mismatched hostnames. A sophisticated attacker possessing a certificate signed by your own CA *with the correct hostname* would fool even `verify-full`. We test how CA private keys are protected or exposed in Kubernetes in Phase 2 and Phase 4.

## Phase 2: Percona Defaults (Path A & Path B)

### Path A: Percona Built-in PKI

#### 1. Target Architecture & Issuers
- **Root CA:** A single internal CA generated by the operator: `CN=postgres-operator-ca`.
- **Certificate Issuance:** Both the Postgres database instances (`cluster1-cluster-cert`) and PgBouncer instances (`cluster1-pgbouncer`) are signed by the exact same CA.
- *Evidence:* [phase2-path-a-postgres-cert-sans.txt](evidence/phase2-path-a-postgres-cert-sans.txt), [phase2-path-a-pgbouncer-cert-sans.txt](evidence/phase2-path-a-pgbouncer-cert-sans.txt)

#### 2. CA Key Material Stored in Namespace Secret
- The Secret `cluster1-cluster-ca-cert` contains both `root.crt` AND `root.key`.
- **Security Impact:** The CA private key is stored in the namespace, readable by anyone with Secret access. Anyone with read permissions to Secrets in `pg-lab` can extract the private key and issue trusted certificates.
- *Evidence:* [phase2-path-a-ca-secret-keys.txt](evidence/phase2/phase2-path-a-ca-secret-keys.txt), [phase2-path-a-secrets-list.txt](evidence/phase2/phase2-path-a-secrets-list.txt)

#### 3. Plaintext Traffic Rejection
- **PgBouncer:** Explicitly requires SSL by default; plaintext connections are rejected with `FATAL: SSL required`.
- **Postgres Primary:** The operator generates `hostssl` rules in `pg_hba.conf` by default. Plaintext connections fail with:
  `FATAL: no pg_hba.conf entry for host "127.0.0.1", user "cluster1", database "cluster1", no encryption`
- *Evidence:* [civo-path-a-pgbouncer-disable-without-root.txt](evidence/phase2/civo-path-a-pgbouncer-disable-without-root.txt), [civo-path-a-postgres-disable-without-root.txt](evidence/phase2/civo-path-a-postgres-disable-without-root.txt)

#### 4. Subject Alternative Name (SAN) Grid
The operator automatically generates SANs covering all four internal Kubernetes DNS patterns:
1. Short Name: `cluster1-pgbouncer` / `cluster1-primary`
2. Name + Namespace: `cluster1-pgbouncer.pg-lab` / `cluster1-primary.pg-lab`
3. Name + Namespace + Service: `cluster1-pgbouncer.pg-lab.svc` / `cluster1-primary.pg-lab.svc`
4. Fully Qualified Domain Name (FQDN): `cluster1-pgbouncer.pg-lab.svc.cluster.local` / `cluster1-primary.pg-lab.svc.cluster.local`

All four hostname forms successfully negotiated TLSv1.3 with `sslmode=verify-full`:
- *Evidence:* [phase2-path-a-pgbouncer-verify-full-short.txt](evidence/phase2/phase2-path-a-pgbouncer-verify-full-short.txt), [phase2-path-a-pgbouncer-verify-full-name-ns.txt](evidence/phase2/phase2-path-a-pgbouncer-verify-full-name-ns.txt), [phase2-path-a-pgbouncer-verify-full-name-ns-svc.txt](evidence/phase2/phase2-path-a-pgbouncer-verify-full-name-ns-svc.txt), [phase2-path-a-pgbouncer-verify-full-fqdn.txt](evidence/phase2/phase2-path-a-pgbouncer-verify-full-fqdn.txt), [phase2-path-a-postgres-verify-full-fqdn.txt](evidence/phase2/phase2-path-a-postgres-verify-full-fqdn.txt)

**Localhost Contrast:**
When connecting over local port-forwarding using `host=localhost` with `sslmode=verify-full`, libpq evaluated all SANs and rejected the connection due to hostname mismatch (`server certificate does not match host name "localhost"`):
- *Evidence:* [phase2-path-a-pgbouncer-verify-full-localhost-mismatch.txt](evidence/phase2/phase2-path-a-pgbouncer-verify-full-localhost-mismatch.txt), [phase2-path-a-postgres-verify-full-localhost-mismatch.txt](evidence/phase2/phase2-path-a-postgres-verify-full-localhost-mismatch.txt)

#### 5. Connection Matrix
The full 12-row connection matrix was executed against both PgBouncer and Postgres Primary:
- Without a root CA, `require` connects blindly (unauthenticated TLS).
- With `civo-ca.crt`, `verify-full` connects and verifies the identity of the server.
- *Evidence:* [evidence/phase2/](evidence/phase2/)

#### 6. Cross-Namespace Distribution Dilemma
- Kubernetes Secrets cannot be mounted across namespaces.
- Because `cluster1-cluster-ca-cert` bundles `root.key` with `root.crt`, distributing the root CA to client applications in other namespaces forces teams to either copy the private key or abandon verification by defaulting to `sslmode=require`.

### Path B: cert-manager

#### 1. Issuer Architecture
When `cert-manager` is present on the cluster, Percona Operator's `auto` policy automatically creates cert-manager resources:
- `cluster1-ca-issuer`: An in-namespace `Issuer` with `spec.selfSigned: {}`.
- `cluster1-tls-issuer`: An in-namespace `Issuer` with `spec.ca.secretName: cluster1-cluster-ca-cert`.
- *Evidence:* [phase2-path-b-issuers-certificates.txt](evidence/phase2/phase2-path-b-issuers-certificates.txt), [phase2-path-b-issuers-spec.txt](evidence/phase2/phase2-path-b-issuers-spec.txt)

#### 2. CA Key Material Stored in Namespace Secret
- Inspecting Secret `cluster1-cluster-ca-cert` shows keys: `["ca.crt", "tls.crt", "tls.key"]`.
- **Architectural Discovery:** Even with `cert-manager` in place, the default Percona integration generates a local, in-namespace CA. Therefore, the CA private key is **stored in the namespace, readable by anyone with Secret access**, presenting the exact same threat model as Path A.
- *Evidence:* [phase2-path-b-ca-secret-keys.txt](evidence/phase2/phase2-path-b-ca-secret-keys.txt), [phase2-path-b-secrets-list.txt](evidence/phase2/phase2-path-b-secrets-list.txt)

#### 3. Subject Alternative Name (SAN) Grid & Authority
- Both Postgres primary (`cluster1-cluster-cert`) and PgBouncer (`cluster1-pgbouncer-frontend-tls`) are signed by the same cert-manager CA (`CN=cluster1-ca`).
- The SANs generated by cert-manager cover the identical four internal Kubernetes DNS variants as Path A.
- *Evidence:* [phase2-path-b-postgres-cert-sans.txt](evidence/phase2/phase2-path-b-postgres-cert-sans.txt), [phase2-path-b-pgbouncer-cert-sans.txt](evidence/phase2/phase2-path-b-pgbouncer-cert-sans.txt)

#### 4. Hostname Grid & Localhost Contrast
- Connecting via the cluster FQDN with `sslmode=verify-full` and `civo-ca-path-b.crt` successfully connected over TLSv1.3.
- Connecting with `host=localhost` failed with:
  `psql: error: server certificate for "cluster1-pgbouncer.pg-lab.svc.cluster.local" (and 3 other names) does not match host name "localhost"`
- *Evidence:* [phase2-path-b-pgbouncer-verify-full-fqdn.txt](evidence/phase2/phase2-path-b-pgbouncer-verify-full-fqdn.txt), [phase2-path-b-pgbouncer-verify-full-localhost-mismatch.txt](evidence/phase2/phase2-path-b-pgbouncer-verify-full-localhost-mismatch.txt)

#### 5. Connection Matrix (PgBouncer & Primary)
The automated 12-row connection matrix was executed against both PgBouncer and Postgres Primary under Path B:
- `disable` fails on both endpoints (`FATAL: SSL required` on PgBouncer; `FATAL: no pg_hba.conf entry ... no encryption` on Postgres Primary).
- `require` connects without validating the CA.
- `verify-full` connects and verifies the endpoint when `civo-ca-path-b.crt` is supplied.
- *Evidence:* [evidence/phase2/](evidence/phase2/)

## Phase 3: Impostor Tests (The Correct-Hostname Gap)

### 1. Threat Model & Scope
> [!IMPORTANT]
> **Framing:** This finding assumes an attacker who possesses read permissions to Kubernetes Secrets within the database namespace (or has compromised an application in that namespace), **not a remote network break**. Because Percona's built-in PKI stores the CA private key (`root.key`) directly inside the namespace Secret `cluster1-cluster-ca-cert`, anyone with Secret read access obtains the cluster's root signing authority.

### 2. The Attack Simulation
1. **Key Extraction:** The operator's CA private key (`root.key`) was extracted from Secret `cluster1-cluster-ca-cert`.
2. **Targeted Certificate Minting:** A new server certificate was minted using the extracted CA key, stamped with the legitimate cluster primary hostname as a Subject Alternative Name:
   - CN / SAN: `cluster1-primary.pg-lab.svc.cluster.local`
   - Issuer: `CN=postgres-operator-ca`
   - *Evidence:* [impostor-cert-details.txt](evidence/phase3/impostor-cert-details.txt)
3. **Impostor Deployment:** An isolated database server was started presenting this certificate.

### 3. Client Behavior Under Strict `verify-full`
A client was configured with maximum TLS security:
- `sslmode=verify-full`
- `sslrootcert=civo-ca.crt` (the legitimate public CA certificate)
- `host=cluster1-primary.pg-lab.svc.cluster.local`

**Result: FOOLED (COMPROMISED)**
- The client validated the CA signature against `civo-ca.crt` -> **Passed**.
- The client verified that the server certificate matched the target hostname -> **Passed**.
- An encrypted TLSv1.3 session was established with the impostor server without any warning or error.
- *Evidence:* [impostor-verify-full-conninfo.txt](evidence/phase3/impostor-verify-full-conninfo.txt)

### 4. Key Takeaway & Architecture Implication
In Phase 1, `verify-full` was sufficient to reject all three impostors because the attacker lacked the trusted CA private key.

However, in Path A, **`verify-full` completely fails to protect the client** once the namespace Secret is read. The client-side TLS handshake cannot distinguish between the legitimate database and an impostor server minted with the same cluster CA.

> [!NOTE]
> **Path B Implication:** Switching to `cert-manager` only solves this problem if the CA signing key is stored **outside** the application/database namespace (e.g. via a `ClusterIssuer` backed by HashiCorp Vault or a dedicated root namespace). If cert-manager is configured with an in-namespace `Issuer`, the CA private key remains in an in-namespace Secret, leaving the attack surface unchanged.
